## 1. 交付物定义

一句话定义本阶段交付物：

> **一块插着 USB、连着办公室 Wi-Fi 的 ESP32-S3 BOX，在办公室电脑的浏览器里打开一个网址，能看到自己（或任何对着摄像头的物体）的实时画面；按下板子上的任意一个实体按钮，浏览器页面立刻弹出一句可配置的中文提示。**

### 1.1 验收标准（能过就是能过，不能过就是不能过）

| 编号 | 验收项 | 判定方式 | 必须满足 |
| --- | --- | --- | --- |
| A1 | 设备上电后自动连上办公室 Wi-Fi | 串口日志打印出 IP 地址 | 拿到内网 IP，如 `192.168.1.123` |
| A2 | 电脑浏览器能打开设备提供的页面 | Chrome 访问 `http://<设备IP>:8080/` | 页面 200，不超时 |
| A3 | 浏览器能看到实时画面 | 画面持续刷新，能看到人脸 | 刷新间隔 ≤ 1 秒 |
| A4 | 画面质量可接受 | 人脸清晰可辨 | 分辨率 ≥ 320x240，帧率 ≥ 10fps |
| A5 | 按板子按钮，网页弹出提示 | 按下 BOX 侧面的实体按钮 | 3 秒内网页弹出一句中文 |
| A6 | 提示内容可自定义 | 改一行配置重新烧录 | 不改业务逻辑，只改字符串 |
| A7 | 断网自动恢复 | 拔掉 Wi-Fi 10 分钟后插回 | 设备自动重连，无需重启 |
| A8 | 连续运行不崩 | 连续跑 8 小时 | 无重启，无内存泄漏导致的崩溃 |

**A1～A5 是本阶段的通过线。A6～A8 是加分项。**

### 1.2 非目标

- ❌ 不追求画面流畅——卡顿可以接受，**能看见**就行
- ❌ 不追求手机也能看——电脑浏览器能看就够（但**接口不许写死**，为后面留路）
- ❌ 不追求 24 小时不间断——先做到 8 小时
- ❌ 不做美观的 UI——一个 `<img>` 加一个弹窗就是全部
- ❌ 不写优雅的架构——**能跑比好看重要一百倍**
- ❌ 不做多路并发——一路就够

## 3. 技术方案

### 3.1 画面怎么传过去（这是本阶段唯一的核心技术问题）

有三条路，本阶段选**第二条**：

#### 方案 A：板子自己开 Web 服务器，电脑去访问板子（HTTP MJPEG）

- 板子连上 Wi-Fi 后起一个 HTTP 服务器，电脑浏览器访问 `http://<板子IP>:8080/`
- 摄像头帧用 MJPEG（`multipart/x-mixed-replace`）推给浏览器
- ✅ **优点**：最简单的方案，几乎零配置，**板子不需要知道电脑在哪**（这是关键——板子做 TCP 服务端，电脑做客户端）
- ✅ 电脑和板子在同一网络，谁先启动都无所谓
- ❌ 缺点：每次只有一个人能看；画质受 Wi-Fi 带宽限制（但 MJPEG 320x240 也就几百 kbps，够用）
- ❌ 缺点：板子做 HTTP 服务器比做客户端复杂一点点

#### 方案 B：板子做客户端，主动推到电脑上（TCP / HTTP POST）

- 板子连上电脑在局域网开的服务，主动 POST 帧过去
- ✅ 优点：电脑端是"接收者"，语义更符合"远程看护"（将来子女端连过来就是同一套）
- ❌ 缺点：电脑得先起服务，板子得知道电脑 IP，配置步骤多
- ❌ 缺点：多客户端要自己做

#### 方案 C：巴法云 / 阿里云物联网等免费物联网平台中转

- ✅ 优点：不用在同一局域网也能看，**这正是最终产品要的样子**
- ✅ 优点：几行代码就通，适合快速验证"能不能远程看"
- ❌ 缺点：**依赖第三方平台，有账号/密钥/协议学习成本**，且免费套餐有并发和流量限制
- ❌ 缺点：平台协议（MQTT 等）和我们的最终自建方案不一致，验证完还要重写

**决策：本阶段走方案 A。** 理由：

1. **验证目标只是"画面能看见"**，方案 A 用最少的活动部件达成
2. 方案 A 是**单向的**（板子→电脑），硬件负担最小，最不容易因为"网络调不通"卡住
3. 方案 C 看起来"更接近产品"，但**它是把"能不能连通互联网"的风险和"能不能出图"的风险绑在一起**——出问题时你分不清是板子的锅还是平台的锅
4. 方案 B 的"板子主动推"模型在**方案 A 里天然支持**：板子 HTTP 服务器可以同时开放一个 `POST /event` 接口，按键时电脑去……不对，是板子去 POST 电脑。

> **修正与统一**：为了 M2 的按键功能不被卡在"电脑得先起服务"上，最终采用**混合方案**：
> - **画面**：板子开 HTTP 服务器（方案 A），电脑访问 `http://<板子IP>:8080/`
> - **按键事件**：板子同时开一个小端口（如 `8090`）作为 TCP 客户端，**主动连到电脑的 `5555` 端口**发一句话；电脑端用一个小 Python 脚本收，收到了就通过 `POST /notify` 告诉板子，板子再在网页画面上弹提示
>
> 这样做的取舍是：**按键事件走"板子主动推"（因为电脑可能不在同一网段/需要主动通知），画面走"电脑主动拉"（因为拉取更稳、功耗更低）**。两者方向相反不冲突，各自用各自最省事的方式。
>
> **如果第二步太难，允许降级**：按键事件也可以走方案 A 的同一个 HTTP 服务器——电脑页面用轮询 `GET /event` 每 500ms 问一次板子"有没有新事件"。**这个降级方案必须保留**，因为它零额外配置，是保底。

#### 3.1.1 最终选型结论

| 环节 | 选型 | 复杂度 |
| --- | --- | --- |
| 画面传输 | 板子 HTTP 服务器 + MJPEG | 中（ESP-IDF 官方 http_server 例程有现成代码） |
| 网页显示 | 电脑浏览器打开 `http://<板子IP>:8080/`，纯 HTML `<img>` | 低 |
| 按键上报 | **首选**板子 TCP 客户端 → 电脑 `:5555`；**保底**网页轮询 `GET /event` | 低（保底方案 5 行代码） |
| 电脑端接收 | Python 3 脚本（已有 Python 3.12.10） | 低 |

**关键：任何一步卡住，立刻切降级方案，不要死磕。**

### 3.2 固件架构

```
┌───────────────────── ESP32-S3 BOX ─────────────────────┐
│                                                          │
│  cam_task ──► JPEG 帧缓冲（PSRAM）                       │
│     │                                                    │
│     ├──► http_server: GET /        → MJPEG 多段响应     │
│     ├──► http_server: GET /event   → 待处理按键事件      │
│     └──► http_server: GET /health  → 状态 JSON           │
│                                                          │
│  btn_task ──► 读 GPIO（按键）                            │
│     │                                                    │
│     ├──► 写入事件队列 ──► GET /event 轮询可取           │
│     └──► TCP 客户端 ──► 电脑 :5555 发 JSON              │
│                                                          │
│  wifi_task ──► 连接办公室 Wi-Fi，断线指数退避重连        │
│                                                          │
└──────────────────────────────────────────────────────────┘
                          │ Wi-Fi
                          ▼
┌──────────────────── 办公室电脑 ─────────────────────┐
│  浏览器 ──► http://<板子IP>:8080/  ──► 看画面          │
│     ▲                                            │    │
│     │ POST /notify (收到按键事件)                 │    │
│  页面 JS ◄──── 收到事件 → 弹出中文提示 ─────────┘    │
│                                                        │
│  recv_event.py ──► 监听 :5555，收到 → POST /notify     │
└────────────────────────────────────────────────────────┘
```

### 3.3 帧格式与配置

- **编码**：MJPEG（板子 OV2640 硬件出 JPEG，ESP-IDF 的 `esp32-camera` 组件直接给 JPEG 帧）
- **不使用 H.264**：ESP32-S3 没有硬件 H.264 编码器，MJPEG 是唯一现实选择
- **分辨率**：起步 **320x240**（VGA 会明显吃带宽，320x240 足够看清"有个人"）
- **帧率**：目标 10fps，实测多少算多少
- **HTTP 响应头**：`Content-Type: multipart/x-mixed-replace; boundary=frame`

### 3.4 页面内容（全部要求，最小实现）

```html
<!DOCTYPE html>
<html lang="zh-CN">
<head><meta charset="utf-8"><title>远程看护盒子 - 可行性验证</title></head>
<body>
  <h1>远程看护盒子（可行性验证）</h1>
  <img id="cam" src="http://<设备IP>:8080/stream" />
  <div id="alert" style="display:none"> <!-- 事件出现时显示 --> </div>
  <script>
    // 每 500ms 轮询 /event；有新事件就显示 #alert
    // 同时 POST /notify 通知板子（让板子屏幕也能亮一下）
  </script>
</body>
</html>
```

**验收只看两件事**：画面在动、字弹出来了。样式随便。

### 3.5 按键事件

- **触发**：短按板子上任意实体按钮（松开即触发，避免长按重复）
- **内容**：默认一句 `"老人按了求助按钮"`，**必须是可改的一行字符串常量**
- **上报格式**：JSON，例如 `{"type":"button","msg":"老人按了求助按钮","ts":1720000000}`
- **网页行为**：弹出一个可见的提示（可以用原生 `alert()`，不做 UI）
- **板子行为**：板载 LCD 亮一下显示同一句话 + 蜂鸣器响一声（如果硬件有）

### 3.6 关键技术配置（ESP-IDF sdkconfig）

这些是**摄像头能不能初始化成功的命门**，必须逐项确认：

| 配置项 | 值 | 为什么 |
| --- | --- | --- |
| `CONFIG_ESPTOOLPY_FLASHSIZE_16MB` | `y` | 模组是 N16R8，16MB Flash |
| `CONFIG_ESPTOOLPY_FLASHSIZE` | `"16MB"` | 同上 |
| `CONFIG_SPIRAM_MODE_OCT` | `y` | **最关键**，Octal PSRAM 不开，摄像头帧缓冲直接初始化失败 |
| `CONFIG_SPIRAM_SPEED_80M` | `y` | 8MB PSRAM 跑 80M |
| `CONFIG_SPIRAM_USE_MALLOC` | `y` | 让内部堆能用 PSRAM |
| `CONFIG_SPIRAM_MALLOC_ALWAYSINTERNAL` | `4096` | 内部堆保留 4KB |
| `CONFIG_ESP32S3_BOX_BOARD` | `y` | 正点原子 BOX 的 board config，省掉自己配引脚 |
| `CONFIG_OV2640_SUPPORT` | `y` | 摄像头驱动 |

**如果 `Camera init failed with error 0x105`，99% 是 PSRAM Octal 那三项没配对。**

## 5. 风险清单（只列会真正卡住本阶段的）

| 风险 | 概率 | 影响 | 应对 |
| --- | --- | --- | --- |
| **PSRAM 没开 Octal，摄像头初始化失败** | 高 | 阻塞 M1 | 严格核对 sdkconfig 八项；参考 `0x105` 报错对照表 |
| 办公室 Wi-Fi 只有 5G / 开了 WPA3 | 中 | 阻塞 M1 | 提前确认路由器开 2.4G 兼容；备一个手机热点 |
| 手机热点有设备数限制或限速 | 中 | 画面卡 | 优先用办公室路由器；热点仅作备选 |
| 板子 IP 每次上电都变 | 高 | 每次都要改网址 | 用 mDNS 主机名（`esp32s3-box.local`）或 DHCP 静态绑定 |
| MJPEG 带宽不够，画面卡成幻灯片 | 中 | 体验差但可接受 | 降分辨率到 320x240 或 240x180；降帧率到 5fps |
| 正点原子例程依赖的 IDF 版本与装的 v5.3 不匹配 | 中 | 编译报错 | 先看例程 README 的 IDF 版本要求，不符就装对应版本 |
| 电脑没装 Python 或端口被占 | 低 | 阻塞 M2 | 已装 Python 3.12.10；换端口 |
| 板子供电不稳（USB 电流不足） | 低 | 随机重启 | 换 USB 口/线；不用 USB Hub |

## 6. 下一步的岔路口

M3.3 评估结论出来后，只有三种走向，**由评估结论决定，不由情绪决定**：

### 走向 A：假设成立，且团队愿意投人力做完整产品

→ 回到 `开发需求文档.md` v1.0，从 M3 设备上云开始往下做。
→ 建议顺序：设备上云推流 → 极简网页/App 远程看（先不做小程序）→ 数据库与告警 → 内容干预。

### 走向 B：假设成立，但人力/时间只够做"能用的东西"

→ 不做完整后台，只做**"板子 + 一个网页 + 微信通知"**三件套。
→ 这已经足够作为**毕业设计/课程项目**交付，且对老人家庭是真实有用的。

### 走向 C：假设不成立（画面出不来 / 不稳定）

→ 停下来，查清楚是硬件问题还是代码问题。
→ 备选硬件：换一块 ESP32-S3-DevKitC + OV2640 摄像头模组（便宜且通用），或换用树莓派。
→ **不要在假设没验证时就规划三个月工期。**
