## 0. 一句话现状

> **摄像头的活儿干完了，音频的活儿也干完了大半，但这两条链路都还没在"远程"这件事上闭环。**

## 1. 需求文档到底要做什么（把 v1.0 摊开讲）

### 1.1 产品一句话

> 一个放在老人家里的 ESP32-S3 BOX 盒子，配子女手机上一个小程序。
> **子女不在家的时候，出事了他要知道。**

### 1.2 前台只做三件事（子女端首页仅此三块，不许堆指标）

| # | 卡片 | 内容 |
| --- | --- | --- |
| ① | 今天动了没有 | 老人今天有没有走动/起身，最近一次活动时间，距今多久 |
| ② | 有事没事 | 当前是否有异常：长时间没动、呼叫没回应、按了求助键、设备离线 |
| ③ | 点一下就能看 | 远程打开实时画面，或直接发起语音通话 |

### 1.3 完整能力清单（12 块）

| 域 | 能力 | 归属 |
| --- | --- | --- |
| 设备感知 | 摄像头 MJPEG 上行、人形/运动检测、麦克风采集、按键、屏幕提示、设备在线状态 | 固件 |
| 设备执行 | 抓拍、播放下行语音、播放干预内容、屏幕提示文案 | 固件 |
| 传输 | 单条 WSS 长连接承载视频/音频/事件/控制 | 固件 ↔ 云 |
| 媒体网关 | 收流、出 FLV（小程序）/ HLS（App）、转码、抓拍、转发对讲下行 | 服务端 |
| 业务 API | 设备注册绑定、在线状态、活动历史、告警 CRUD、会话记录、内容库、家庭成员与值班顺序、周报 | 服务端 |
| **规则引擎** | 活动判定、告警分级 L0-L3、去抖冷却、升级链、闭环统计、内容触发 | 服务端（**产品本体**） |
| 提醒通道 | App 推送 / 微信订阅消息 / 短信 / 值班电话 | 服务端 |
| 双端客户端 | Flutter App（主）+ 微信小程序（轻量） | 客户端 |
| 内容干预 | 音乐疗法 / 久坐干预 / 疼痛管理三类内容库，VAD 判定命中率 | 端到端 |
| 安全隐私 | 一机一密钥 + HMAC、全链路 TLS、家庭隔离、留存期限、可删除导出 | 端到端 |
| 试点运营 | 1 个真实家庭跑 4 周，误报率 ≤ 20% | 运营 |

### 1.4 v1.0 明确不做

机构版、护工排班、护理记录归档、多租户 SaaS、跌倒检测商用准确率、老人端 App、语音唤醒、医疗诊断级结论。

### 2.3 当前最硬的阻塞 🔴

**I2C 总线被硬件拉低，AW9523B 无应答。** 最近一次启动日志 `bootF.log` 显示：

```
SDA=0 SCL=0  <== 仍被拉低
aw9523b: AW9523B 无应答 (addr=0x59): ESP_ERR_TIMEOUT   (连续 20 次重试全失败)
共 0 个地址应答
```

影响面：AW9523B 负责 **摄像头供电（XIO15 复位）、音频 VBAT/3V3 使能、功放使能、LCD 背光、K1/K2 按键**。
现在能出图、能出声，是因为板子当前是热启动状态且关键外设已被前一次运行配置过；**冷启动很可能起不来**。

这条必须在动任何新功能之前解决，否则后面每次烧录都是赌博。

## 4. 分阶段任务拆解

### 4.0 🔴 P0 解阻塞（预计 1–2 天）

| # | 任务 | 完成标准 |
| --- | --- | --- |
| P0.1 | 定位 I2C 被拉低的真凶 | 冷启动下 `SDA=0 SCL=0` 能解释清楚是硬件短路还是固件没释放引脚 |
| P0.2 | 恢复 AW9523B 应答 | `awregs` 打印出非 0xFF 的寄存器快照 |
| P0.3 | 冷启动回归 | **拔 USB 等 10 秒再插**，能出图 + 出声 + LCD 亮 + 按键有效 |
| P0.4 | PC 接收端常驻化 | `recv_event.py` 加 `--daemon`，开机自启，`:5556` 监听稳定 |

> 上一轮已经查到一半：怀疑固件在 `i2c_set_pin` 后没把引脚还给 GPIO，导致外部上拉/器件把总线拽死；也怀疑过是 esp_codec_dev 的 I2C 驱动和旧版 `driver/i2c.h` 抢同一个端口。**两件事都要验证，不能靠猜。**

| # | 任务 | 完成标准 |
| --- | --- | --- |
| P1.1 | `pc_receiver/recv_audio.py` | 拉 `/audio/alaw` → 解 A-law → 存 WAV → 播放 |

### 4.2 🟠 P2 远程通路（预计 1–2 周）

**这是「远程看护」四个字真正的落地处，也是当前最大的架构缺口。**

现在板子只能被同一个局域网内的电脑访问。要让在外地的子女看到，必须解决"板子怎么主动连出去"。

| 方案 | 做法 | 优点 | 缺点 |
| --- | --- | --- | --- |
| **A. WSS 单连接（推荐，v1.0 原定）** | 板子主动连云端 `wss://`，一条连接承载视频/音频/事件/控制 | 与 v1.0 文档一致；穿透 NAT；一套协议走天下 | 要写 WS 客户端 + 帧封包 + 断线重连；云端要起服务 |
| B. Cloudflare Tunnel / frp | 板子 HTTP 走隧道出去 | 改造成本最低，1 天能出画面 | 带宽按隧道走，成本高；音频上行/下行不对称；不是最终架构 |
| C. 巴法云 / 阿里云 IoT 中转 | 走 MQTT 第三方平台 | 几乎不用写代码 | 协议和最终方案不一致，验证完要重写 |

**建议**：**A 为目标架构，B 作为"让导师/同学先看到效果"的临时演示通道。**
两者不冲突——协议封包层设计成和 B 复用同一套 `ws_uplink` 组件。

| # | 任务 | 完成标准 |
| --- | --- | --- |
| P2.1 | 帧封包层 | 按 v1.0 §3.6：`magic(2B) 0xAA55 \| ver(1B) \| type(1B) \| seq(4B BE) \| ts(8B) \| len(4B BE) \| payload` |
| P2.2 | `ws_uplink` 组件 | WSS 连接 + 断线指数退避 + 心跳 + 缓冲重传 |
| P2.3 | 本地 WS 模拟服务 | Python 脚本当云端，验证固件能推流 |
| P2.4 | 媒体网关雏形 | 收流 → 出 FLV + HLS（FFmpeg 即可，SRS 后面再上） |
| P2.5 | 公网可达 | 临时用隧道打通，异地手机能看到画面 |
| P2.6 | 鉴权 | 一机一密钥 + HMAC-SHA256 签名，令牌可吊销轮换 |

## 5. 关于「蓝牙」——需要你拍板

**原始需求文档 v1.0 从头到尾没有蓝牙**（全文只提 2.4GHz Wi-Fi）。你这次问起蓝牙，我先说清楚它值不值得做：

| 蓝牙用途 | 值不值 | 说明 |
| --- | --- | --- |
| **子女首次给盒子配网** | ⭐⭐⭐ 最值得 | 现在得改固件里的 `WIFI_SSID` 宏重烧，普通人根本做不到。加一个 BLE 配网，子女扫码/输密码即可 |
| 老人佩戴设备接入门磁/跌倒传感器 | ⭐⭐ 现阶段不做 | v1.0 明确砍掉跌倒检测 |
| 接蓝牙音箱播干预内容 | ⭐ 收益低 | 盒子自带喇叭够用 |
| 盒子当蓝牙音箱被手机播内容 | ⭐ 收益低 | 同上 |

**我的建议：把蓝牙收敛成「BLE 配网」这一个用途**，在 P2（远程通路）阶段顺带做——
因为那一步本来就要引入 Wi-Fi 配网逻辑，BLE 配网正好挂在同一个位置。

如果你要的是别的蓝牙用途（比如接健康手环、老人随身呼叫器），说一声，那是完全不同的设计。

## 7. 下一步（三选一，等你拍板）

| 选项 | 做什么 | 理由 |
| --- | --- | --- |
| **① 先解阻塞**（推荐） | 查清 I2C 被拉低 + 冷启动回归 + PC 端常驻 | 现在每次烧录都带赌博风险，不解掉后面全是空中楼阁 |
| ② 先通音频 | 直接写 `recv_audio.py` + 对讲页面 | 板子接口已就位，3 天能看到"子女说话老人听见"，成就感强 |
| ③ 先通远程 | 上 WSS + 临时隧道 | 这是产品的核心差异点，但依赖 ①（网络不稳时没法分辨是网络问题还是板子问题） |

**我的推荐是 ① → ② → ③**，理由：① 是所有事的地基，且现在板子处于"热启动能用、冷启动未知"的状态，
这个不确定性会污染后面每一个阶段的调试。
